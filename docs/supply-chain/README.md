# PromptVault Lite — Supply-Chain Documentation (SBOM · Provenance · Reproducibility)

> Scope: issue #296 sale-asset hardening. This document is written for a
> technical evaluator of the repository (transfer, audit, distribution or
> acquisition diligence). It states precisely what is produced, how it is
> verified, and what is **not** claimed.

## What PromptVault Lite is

PromptVault Lite is a local-first prompt-management desktop application
(Tauri 2 / React frontend, Rust backend) for Linux: directory-based prompt
libraries with YAML-frontmatter metadata, offline quality/hygiene analysis,
and export. Local-first is a hard posture: analysis is offline, there is no
cloud service, no telemetry, and no account. License: MIT
([`LICENSE`](../LICENSE)). Current release at the time of writing: **v1.13.3**
(Linux `.deb` / `.rpm` / AppImage, published from the fail-closed release
pipeline in `.github/workflows/release.yml`).

573 cargo crates = 1464 components**, all represented in the SBOM.

## SBOM (CycloneDX 1.6)

- **Generator:** `scripts/supply-chain/generate-sbom.mjs` — zero external
  dependencies, strict parsers for the exact lockfile formats
  (`scripts/supply-chain/lib/lockfiles.mjs`). Deterministic:
  - `serialNumber` is a UUIDv5 of `promptvault-lite/sbom/<version>/<commit>`;
  - `metadata.timestamp` is the tagged commit's author date (passed in, never
    wall-clock);
  - components/dependency arrays are sorted.
  Same (source, version, commit, timestamp) ⇒ **byte-identical SBOM**. CI
  proves this on every run: generate twice, `cmp`, fail on difference
  (`.github/workflows/supply-chain.yml`).
- **Contents:** root component `pkg:github/Mueller-Systems-Lab/promptvault-lite@<version>`
  (bound to the release via `promptvault:source_commit`), every lockfile
  entry as a component with purl (`pkg:npm/…`, `pkg:cargo/…`), licenses from
  the committed registry-metadata cache, dependency edges from the lockfile
  graphs (npm `snapshots:` section, cargo `[[package]] dependencies`).
  Ambiguous edges are skipped, never guessed.
- **Licenses:** `scripts/supply-chain/license-data.json` is a committed,
  reviewable cache fetched once from registry.npmjs.org and crates.io by
  `scripts/supply-chain/fetch-license-metadata.mjs` (regenerate after every
  lockfile change). Generation is offline.
- **Validation:** `scripts/supply-chain/validate-sbom.mjs` is an independent
  structural validator (no shared code with the generator): CycloneDX 1.6
  envelope, root identity, commit binding, purl scheme, duplicate/dangling
  refs, minimum counts, required components, and a leak scan (private paths,
  the private corpus marker, token patterns) that fails closed. It is the
  engine of release gate **G9** (`--require-sbom`): a future release cannot
  pass verification without a staged, hash-bound, structurally valid SBOM.
- **Release integration:** the release workflow generates the SBOM for the
  tagged commit, stages it as `release-staging/sbom/promptvault-lite-<v>-sbom.cdx.json`,
  records it in the release manifest (`sbom: {filename, sha256, size, …}`),
  and publishes it as a release asset. `SHA256SUMS.txt` deliberately remains
  the packages-only download-verification contract.

## Build provenance (GitHub artifact attestations)

Future releases and every main-branch SBOM are attested with
[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance),
commit-pinned to `e8998f949152b193b063cb0ec769d69d929409be` (v2.4.0) — no
floating tags on supply-chain actions. The attestation is a SLSA-style
provenance statement binding each artifact digest to:

- source repository and **exact commit**,
- workflow identity and build event/ref,
- build runner and timestamp.

Least privilege: the attesting jobs hold exactly `id-token: write`,
`attestations: write`, `contents: read` and nothing else (asserted by
`scripts/__tests__/supply-chain-workflow.test.js`). PR runs attest nothing
(fork-safety). Verification of a published attestation:
`gh attestation verify <artifact> --repo Mueller-Systems-Lab/promptvault-lite`.

What this mechanism **does not** provide: it does not make the artifacts
reproducible, and it does not vouch for anything beyond the workflow→digest
binding recorded by GitHub.

## Reproducibility — claims and evidence

The terms are used precisely (no conflation):

| Claim | Meaning | Status |
| --- | --- | --- |
| `REPEATABLE_BUILD` | same environment, same source ⇒ same result | tested by the two-clean-build experiment below |
| `BIT_FOR_BIT_REPRODUCIBLE` | independent clean builds ⇒ byte-identical artifacts | see experiment verdict below |
| `REPRODUCIBLE_BUILD_INPUTS` | inputs pinned sufficiently to recreate the build | **PASS** — frozen lockfiles, pinned tool versions in the experiment, documented runner-image caveat |
| `BUILD_PROVENANCE` | verifiable statement of what produced an artifact | **PASS** — GitHub artifact attestations (above) |

### Two-clean-build experiment

`.github/workflows/supply-chain-repro.yml` (manual `workflow_dispatch`)
builds the **same commit twice on two independent runner instances** — no
shared caches, pinned pnpm 9.15.9 / Node 22.11.0 / Rust 1.92.0
(`dtolnay/rust-toolchain@e2a55d2`, commit-pinned), same `RUSTFLAGS` path
remapping as the release workflow — then compares `.deb`/`.rpm`/`.AppImage`
with `scripts/release/repro-compare.mjs`, which hashes both sides and, on
divergence, diagnoses which layer differs (payload mtimes, per-file
differences, ELF build-id) **without patching anything**. The report is
attached as a workflow artifact (`repro-report.json` / `.md`).

Known floating platform inputs (documented, not hidden): the runner image
(`ubuntu-latest`) and its apt packages. The experiment controls everything
above them.

### Experiment results — two clean local builds @ `6ede3103904c3a0d9badac1493b559454997f589` (2026-10-11)

Toolchain context: pnpm 9.15.9, Node v24.11.1, rustc 1.92.0, Linux Mint 22.2
(kernel 6.11.0-17-generic); two fresh clones of the same commit in
`/mnt/nvme-data/pvl-repro-a` / `-b`, each with its own empty `target/`, frozen
lockfiles, release profile (`lto`, `codegen-units=1`), the same
`RUSTFLAGS` path remapping as the release pipeline, builds run serially.
(The shared cargo registry cache only shortens build time; it cannot change
outputs. `.github/workflows/supply-chain-repro.yml` repeats the experiment on
two independent GitHub runners for the cross-environment variant.)

| Artifact | sha256 build A | sha256 build B | byte-identical |
| --- | --- | --- | --- |
| `.deb` | `467276814ee1…` | `25362d766fb5…` | NO |
| `.rpm` | `d6a186de05d6…` | `3908f40876a2…` | NO |
| `.AppImage` | `f53fcf6f0e9f…` | `965ad5868d70…` | NO |

**Diagnosis (the important part):** the divergence is **entirely
packaging-layer timestamps, not code** —

- `.deb`: all 7 payload files **byte-equal**; all 7 differ only in mtime
  (plus archive header ordering).
- `.AppImage` (814 payload files): **0 files with differing bytes**; 372
  byte-equal with differing mtimes, 442 fully equal.
- Main binary `usr/bin/promptvault-lite` extracted from both AppImages:
  **identical sha256 `8b792c4648cb…`** — the compiled artifact is
  bit-identical across the two clean builds.
- `.rpm`: no guaranteed diagnosis tooling on the runner; given the other two
  formats show timestamp-only divergence at equal sizes, the same layer is
  the reasonable working hypothesis (unproven for rpm).

**Classification (honest):**

| Claim | Status |
| --- | --- |
| `REPEATABLE_BUILD` (same environment, same source ⇒ same result) | **PASS for everything the compiler produces** — binaries byte-identical |
| `BIT_FOR_BIT_REPRODUCIBLE` (independent clean builds ⇒ identical packages) | **NOT_YET** — `.deb`/`.rpm`/`.AppImage` embed build-time filesystem mtimes (deb data layer, squashfs mtimes, archive headers) |
| `REPRODUCIBLE_BUILD_INPUTS` | **PASS** — frozen lockfiles, pinned tool versions, documented remapping |
| `BUILD_PROVENANCE` | **PASS** — attestations bind digest ↔ repository/commit/workflow |

Bounded remediation path (not attempted here — it lives upstream, and a
partial fix would not change the verdict): `SOURCE_DATE_EPOCH` support in
Tauri's deb writer and clamped mtimes (`-mkfs-time`/`-all-time` style flags)
in the linuxdeploy/mksquashfs AppImage step. No patching was done to force
hash equality.

## What has NOT been demonstrated (honest limitations)

1. **No claim of bit-for-bit reproducibility is made unless the experiment
   above produced hash-equal artifacts for all three package formats.**
2. The attestation path is exercised on every push (SBOM attestation) and on
   future tag builds (packages + SBOM); v1.13.3 predates it and carries no
   attestations. Its assets are deliberately untouched.
3. The SBOM's license metadata mirrors what the public registries expose;
   `UNKNOWN`/`CUSTOM` entries are surfaced in the inventory for manual review
   rather than guessed.
4. `ubuntu-latest` and its system libraries float between the release build
   and any local reproduction; exact-OS reproduction would need a pinned
   container image (out of scope for this slice).
